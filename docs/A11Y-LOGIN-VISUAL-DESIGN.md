# 登入介面的視覺與互動設計

日期：2026-10-09
前置：`docs/A11Y-ENTRY-AND-AUTH.md`（無障礙規範）、`docs/superpowers/plans/2026-10-09-auth-local-stub.md`（stub 設計）

## 0. 設計判讀與適用範圍

**讀作：** 原生 Android（Flutter）的登入介面，使用者是香港的全盲與低視力人士，
無障礙是硬約束，風格沿用既有的 M3 深色 + 品牌綠 `#2E7D32`。
主要的互動模型是**平台螢幕閱讀器**（TalkBack），不是視覺。

**刻度**：`DESIGN_VARIANCE 3` / `MOTION_INTENSITY 2` / `VISUAL_DENSITY 3`。
密度比一般「信任優先」的 4 再低一級，因為「不誤觸」直接要求更大的間距。

**適用範圍聲明**：原生行動端不在本 skill 的範圍內（它自己第 13 節寫明
「Native mobile: use Apple HIG / Material directly」）。
所以這裡只借用它的推斷紀律：

| 借用的條款 | 用在哪 |
|---|---|
| §0 判讀、§1 刻度 | 本節 |
| §4.2 色彩鎖（單一強調色、不用 AI 紫） | 第 2 節 |
| §4.4 圓角一致性鎖 | 第 2 節 |
| §4.5 完整的互動狀態（載入／空／錯誤） | 第 5 節 |
| §4.11 主題鎖（全頁一個主題） | 第 2 節 |
| §9.G 破折號禁令 | 第 6 節的台詞 |
| §3.C 圖示只用官方圖示庫、不手繪 | 第 2 節 |

**刻意不採用**的條款見第 8 節（那些是落地頁專用的，這裡放進來只會產生噪音）。

## 1. 三個需求拆成可檢查的規則

### 1.1 「不誤觸」（最重要，也最容易做錯）

**關鍵洞察：對全盲使用者，「誤觸」的形態跟對明眼人完全不同。**

明眼人的誤觸是「手指太粗、點到隔壁」。但 TalkBack 的互動模型是
**單指點擊只移動焦點並朗讀，啟動要雙擊**。這本身已經是很好的防誤觸機制，
所以「把按鈕做大」對全盲使用者的幫助有限（但對低視力使用者仍然必要）。

真正的風險是這五種：

1. **探索時不小心雙擊啟動** —— 手指在螢幕上滑動聽取內容，停頓時誤觸
2. **忙線中重複觸發** —— 按了沒反應就再按，送出兩次請求
3. **兩種不同意圖的按鈕相鄰**
4. **只靠手勢才能觸發的動作** —— 盲人發現不了，卻可能誤觸
5. **對話框按鈕文字含糊** —— 只聽到「確定」「取消」時無從判斷

| 規則 | 具體做法 | 為什麼 |
|---|---|---|
| 登入頁**完全沒有破壞性動作** | 登出與刪除帳號只在帳號頁 | 最強的防誤觸就是讓它們不在這裡 |
| 破壞性動作**不相鄰** | 至少 24dp 間隔，且**不是**填色按鈕 | 避免探索時順手觸發 |
| 破壞性動作**用物件命名** | 「刪除帳號」／「保留帳號」，不用「確定」／「取消」 | 只聽得到標籤時，「確定」不知道確定什麼 |
| 對話框**安全選項排在焦點順序第一位** | `AlertDialog` 的 actions 把「保留帳號」放第一個 | 焦點從上往下走，先到安全的那個 |
| 忙線中**停用**主按鈕 | 標籤改「正在登入…」+ liveRegion 播報 | 停用是唯一能真正防重複請求的做法 |
| 輸入框的 IME 動作**不送出** | `TextInputAction.next`，不寫會觸發登入的 `onSubmitted` | 盲人打字時誤按 Enter 不該送出 |
| 進頁面**不自動聚焦輸入框** | 不設 `autofocus` | 否則鍵盤突然彈出並改掉焦點，很困惑 |
| **不用滑動手勢** | 不加 `Dismissible` 之類 | 滑動無法被探索發現，卻容易誤觸 |
| **不用長按隱藏功能** | 所有功能都要能被朗讀出來 | 長按對盲人等於不存在 |
| 可點元素間距 ≥ 16dp、高度 ≥ 56dp | 統一寫進常數 | 低視力與手指粗的使用者都需要（WCAG 2.5.8 要求 24dp 是最低標，這裡遠超） |

### 1.2 「簡潔」

- **一頁一個決定。** 登入頁只有「登入」或「不登入」這一個決定。
- **可點元素上限 5 個**（三種零打字方式 + 電子郵件 + 稍後再說），且**全部垂直堆疊**。
  這個數字跟著「可用的登入方式」走，不是固定值：例如手機沒設指紋時就少一顆。
  > 我原本在這裡寫「≤ 3 個」，但同一節的版面示意圖有 5 個，**是我寫錯了**。
  > 真正的規則不是「按鈕要少到某個數字」，而是「**只有一個決定**，
  > 而且每個按鈕都是那個決定的一個選項」。把它寫成 3 只會逼出一個假的版面。
- **垂直堆疊，不橫向並排。** 並排是誤觸溫床，而且在 200% 字級下一定會擠爆。
- **沒有裝飾**：沒有插圖、沒有輪播、沒有動畫。品牌色只在主按鈕上出現一次。
- **標題左對齊**，不置中。理由很實際：200% 字級下置中會重新排版並跳動，
  左對齊是穩定的。

### 1.3 「簡單上手」

- 進入頁面**立刻朗讀**：「登入頁。登入後可以把未識別的障礙物上傳。不登入也能引導。」
  一句話講完「這是什麼、有什麼用、能不能不做」。
- 焦點從標題開始，往下就是第一顆按鈕，順序與朗讀順序一致。
- 每顆按鈕的文字都是**動作 + 結果**。
- 「稍後再說」與登入按鈕**同級**（同樣全寬、同樣高度），但**在下方**而不是旁邊。

## 2. 視覺規範

| 項目 | 規範 | 依據 |
|---|---|---|
| 主題 | **深色鎖定**，全 App 一個主題，不中途反色 | skill §4.11 |
| 強調色 | **只有一個**：品牌綠 `#2E7D32` 系。錯誤色是語義色，不算第二強調色 | skill §4.2 |
| 禁止 | 不做 AI 紫、不做漸層、不做霓虹外發光 | skill §4.2 / §9.A |
| 對比 | 正文 ≥ **7:1**（AAA），大字 ≥ 4.5:1 | WCAG 1.4.6 |
| 圓角一致性鎖 | 按鈕 **全藥丸**、輸入框 **12**、卡片 **16**，寫進常數並全頁遵守 | skill §4.4 |
| 觸控目標 | ≥ **56dp**（Android 最低是 48dp，這裡刻意加大） | WCAG 2.5.8 之上 |
| 間距 | 頁邊 **24dp**、區塊之間 **24dp**、按鈕之間 **16dp**、破壞性動作之前 **24dp+** | 本文件 1.1 |
| 字級 | 支援系統縮放到 **200% 不截斷**；用 `MediaQuery.textScalerOf`，**禁止固定高度** | WCAG 1.4.4 |
| 圖示 | 只用 **Material Symbols**（Flutter 內建 `Icons`），**不手繪 SVG** | skill §3.C |
| 不用 | emoji、裝飾性圓點、分隔線裝飾 | skill §9.D / §9.F |
| 焦點態 | TalkBack 的綠框之外，再加 **2dp 描邊 + 形狀變化**。**不靠顏色單獨表達** | WCAG 1.4.1 |

> **圓角規則為什麼寫成三種而不是一種**：skill §4.4 允許混合，但要求有明文規則
> 並全頁遵守。按鈕用藥丸是因為它與「可點」的語義綁定；輸入框用 12 是因為
> 藥丸形的輸入框會讓文字看起來被裁掉。這條規則要寫在常數檔裡，不是散在各處。

## 3. 回饋設計：誰出聲、誰震動

這裡有一個真實衝突：**TalkBack 開著時它自己就會朗讀焦點元素。
如果我們的 App 又用自己的 TTS 唸一次，兩隻聲音會疊在一起。**

分流規則（用 `MediaQuery.accessibleNavigation` 判斷）：

| 情況 | TalkBack 開著 | TalkBack 沒開 |
|---|---|---|
| 焦點朗讀 | 交給螢幕閱讀器 | 我們的 TTS |
| 狀態變化（載入、錯誤） | `liveRegion` 補播報 | 我們的 TTS |
| 觸覺回饋 | TalkBack 自己會給 | `HapticFeedback.lightImpact()` |
| 頁面進入的整段說明 | 只在第一次進入時播，避免干擾 | 我們的 TTS |

**為什麼要有觸覺**：盲人按下按鈕後，語音要等 TTS 排隊，觸覺是**立即**的。
「按到了」這三個字用震動回答比用語音快。

⚠️ **這一條尚未在真機驗證**：`MediaQuery.accessibleNavigation` 在 Android 上
是否準確反映 TalkBack 狀態，需要在手機上開／關 TalkBack 各測一次。
**不要因為文件寫得對就直接採用。**

## 5. 狀態機

| 狀態 | 畫面 | 播報 | 出口 |
|---|---|---|---|
| `idle` | 如上方版面 | 進入時那一句 | 3 個登入方式 + 電子郵件 + 稍後再說 |
| `busy` | 主按鈕**停用**、標籤改「正在登入…」 | 「正在登入，請稍候。」立刻播，**不等網路** | 全部按鈕停用（防重複） |
| `failed(network)` | 狀態區顯示錯誤 + 「重試」 | 「連不上網路。引導功能不受影響。」 | 「重試」／「稍後再說」 |
| `failed(providerUnavailable)` | 提示改用其他方式 | 「這台手機沒設定指紋。改用 Google 帳號登入。」 | 其他方式 |
| `failed(accountLocked)` | 狀態區 + 「客服」 | 「帳號暫時被鎖。」 | 「客服」／「稍後再說」 |
| `failed(lastSignInMethod)` | 在帳號頁 | 「這是最後一個登入方式，不能解除。」 | 關閉 |
| `cancelled` | 回到 `idle` | 「已取消，沒有登入。」**不報錯誤** | 重新選擇 |
| `needsLinking` | 對話框 | 「這個信箱已經有帳號了。要用 Google 登入原本的帳號嗎？」 | 「是，連結」／「不，取消」 |
| `email 第一步` | 輸入框 | 「輸入電子郵件地址。」 | 「寄送驗證碼」 |
| `email 第二步` | 驗證碼輸入框 | 「驗證碼已寄出。可以從通知複製貼上。」 | 「驗證並登入」 |

### 帳號頁（已登入）

這是唯一有破壞性動作的地方，規則見 1.1：

```
┌──────────────────────────────────────┐
│ 帳號                                  │
│ mock.user@pathguide.test              │  ← 唯讀資訊，不是輸入框
│ 已連結：Google、Apple                  │
│              24dp                     │
│ ┌──────────────────────────────────┐ │
│ │  登出                             │ │  ← 外框，不是填色
│ └──────────────────────────────────┘ │
│                                      │
│              40dp  ← 刻意的大間隔      │
│                                      │
│         刪除帳號                       │  ← 文字按鈕、error 色、無填色
└──────────────────────────────────────┘
```

刪除的確認對話框：

```
標題：刪除帳號
內容：這會永久刪除你的帳號與上傳紀錄。引導功能不受影響。
      ← 焦點順序：標題 → 內容 → 「保留帳號」→「刪除帳號」
[ 保留帳號 ]   [ 刪除帳號 ]      ← 安全的那個放**前面**
```

## 6. 台詞（英文預設 + 繁體中文）

| 場景 | English | 繁體中文 |
|---|---|---|
| 頁面說明 | Sign in to upload obstacles we could not recognise. Guidance works without signing in. | 登入後可以把未識別的障礙物上傳。不登入也能引導。 |
| 指紋按鈕 | Sign in with fingerprint | 用指紋登入 |
| Google 按鈕 | Sign in with Google | 用 Google 帳號登入 |
| Apple 按鈕 | Sign in with Apple | 用 Apple 帳號登入 |
| 稍後再說 | Not now | 稍後再說 |
| 載入中 | Signing in. One moment. | 正在登入，請稍候。 |
| 成功 | Signed in. | 登入成功。 |
| 取消 | Cancelled. You are not signed in. | 已取消，沒有登入。 |
| 網路失敗 | Cannot reach the network. Guidance still works. | 連不上網路。引導功能不受影響。 |
| 沒有指紋 | This phone has no fingerprint set up. Use Google instead. | 這台手機沒設定指紋。改用 Google 帳號登入。 |
| 需要連結 | That email already has an account. Sign in with Google instead? | 這個信箱已經有帳號了。要用 Google 登入原本的帳號嗎？ |
| 刪除確認 | Delete your account and uploads. Guidance still works. | 這會永久刪除你的帳號與上傳紀錄。引導功能不受影響。 |
| 保留 | Keep account | 保留帳號 |
| 刪除 | Delete account | 刪除帳號 |

**台詞規則**（逐條可檢查）：

- **零 em dash**（skill §9.G）。上面的文案一個都沒有。
- **不用「確定」「取消」「提交」**這類沒有資訊的字。
- **不說方位**（「下方」「右邊」）。盲人沒有這個參考點。
- **教互動，不教位置**：「用 TalkBack 找到『允許』，然後雙擊」。
- **錯誤要說下一步做什麼**，不能只說「失敗了」。

## 7. 驗收清單（機械可查）

- [ ] 登入頁的可點元素 **≤ 5 個**（且數量隨可用登入方式變動，不是固定）
- [ ] 登入頁**沒有任何破壞性動作**
- [ ] 所有可點元素高度 **≥ 56dp**，間距 **≥ 16dp**
- [ ] 破壞性動作與其他元素間隔 **≥ 24dp** 且樣式不是填色按鈕
- [ ] 刪除確認對話框的**焦點順序**：安全選項在破壞性選項之前
- [ ] 忙線中主按鈕**停用**，且狀態變化的播報**早於**網路回應
- [ ] 輸入框的 IME 動作**不會**送出表單
- [ ] 進入頁面**不自動聚焦**任何輸入框
- [ ] 沒有滑動手勢、沒有長按隱藏功能
- [ ] 系統字級 **200%** 下無截斷、無重疊、無橫向溢出
- [ ] 全頁**無僅靠顏色**傳達的資訊
- [ ] 全頁文案 **0 個 em dash**
- [ ] 圓角只出現三種：藥丸（按鈕）、12（輸入框）、16（卡片）
- [ ] 強調色只有品牌綠一個

### 與 TalkBack 配合（第 9 節，逐條可測）

> 前提（第 9.0 節）：**關掉 TalkBack，功能必須完整。** 下面第一條就是在測這件事。

- [ ] **★ 關閉 TalkBack（`accessibleNavigation == false`）時，全流程完整可用**：
      每個狀態變化都有 App 自己的 TTS 播報，不依賴螢幕閱讀器
- [ ] 開啟 TalkBack 時，功能同樣完整
- [ ] 頁面標題有 `Semantics(header: true)`；帳號頁的每一節也都有
- [ ] 狀態區是 `liveRegion`，且**不移動焦點**
- [ ] 忙線中主按鈕帶 `enabled: false`（TalkBack 會唸「已停用」）
- [ ] 每一顆按鈕的語意節點同時有 **label** 與 **hasTapAction**
- [ ] 「圖示 + 文字」的按鈕用 `MergeSemantics`，**不會被唸兩次**
- [ ] **沒有任何**非語意的 `GestureDetector(onTap:)`
- [ ] TalkBack 開著時，App **不發**自己的 TTS（用假 Speaker 斷言零次呼叫）
- [ ] 每一句即時播報 **≤ 12 個字**
- [ ] 錯誤出現後，**下一滑**就到得了「重試」或「稍後再說」
- [ ] `Semantics(label:)` 不與子層 `Text` 重複
- [ ] 對話框標題有 `Semantics(header: true)`

## 8. 刻意不採用的 skill 條款（以及為什麼）

| 條款 | 為什麼不用 |
|---|---|
| Hero 必須塞進首屏、副標 ≤ 20 字 | 那是行銷首屏的規則。登入頁沒有 hero，只有一個決定 |
| Eyebrow 每 3 節最多 1 個 | 登入頁只有 1 個「節」，這條規則沒有對象 |
| Bento 網格、marquee、zigzag | 沒有任何一個適合登入頁，硬套只會製造裝飾 |
| CTA 在桌面不可換行 | 手機上全寬按鈕本來就不換行，但**200% 字級下要允許換行**，
  這是與該條款相反的取捨（可讀性 > 版面整齊） |
| 「必須有真實圖片」 | 登入頁放圖片對全盲使用者是零資訊，對低視力使用者是干擾。
  這裡的視覺資產就是**排版本身** |
| 三欄等寬卡片禁令、logo 牆規則 | 登入頁沒有這些元件 |

## 9. 與 TalkBack 配合：1+1>2

### 9.0 先講清楚前提：**App 必須能單獨完整運作**

這一節講的是「配合」，但**配合不是依賴**。前提是：

> **關掉 TalkBack，這個 App 仍然是一個完整可用的產品。**
> TalkBack 是放大器，不是它的一部分。

這是硬規則，理由是使用者不是只有一種：

| 使用者 | 靠什麼 | 憑什麼能用 |
|---|---|---|
| 沒開 TalkBack 的全盲使用者 | App 自己的 TTS + 觸覺 | 我們的播報與震動是完整的，不是「補充說明」 |
| 低視力使用者（視障人口的大多數） | 視覺 | 56dp 目標、7:1 對比、200% 字級 |
| 還沒學會 TalkBack 的人 | 視覺 + 我們的 TTS | 不要求他先學會一個系統功能才能用 |
| 開著 TalkBack 的人 | TalkBack | 下面的配合讓體驗更好 |

所以本節每一條都要讀成「**加上去會更好**」，不是「少了它就不行」。

**「1+1>2」的定義**：兩者**各自都足夠**，但合起來能做到單獨做不到的事。
判準是：拿掉任一邊，功能仍然完整；兩邊都在時，體驗更好。

### 9.1 我們借 TalkBack 的力（七個機制）

| 機制 | Flutter 寫法 | 為什麼是 1+1>2（單獨做不到什麼） |
|---|---|---|
| **標題導覽** | `Semantics(header: true)` | 使用者可把朗讀控制切成「標題」，**一滑就跳到頁首**，不必逐項滑過整頁。TalkBack 只認得標記，標記要我們給 |
| **即時區域** | `Semantics(liveRegion: true)` | 狀態變化會**主動播出，且不移動焦點**。TalkBack 本身不可能知道我們的登入狀態變了 |
| **停用狀態** | 停用時自動帶上 `enabled: false` | TalkBack 會唸「已停用」。**這是「忙線中停用」能被理解的唯一原因** |
| **本機內容選單** | `CustomSemanticsAction` | 次要／破壞性動作可以放進 TalkBack 自己的選單（上滑再右滑）。**畫面上因此能少一顆按鈕** |
| **畫面範圍** | 對話框路由自帶 `scopesRoute` | 對話框開啟時焦點被正確圈住，不會跑到後面的頁面 |
| **朗讀順序** | `OrdinalSortKey` + `FocusTraversalGroup` | 朗讀順序 = 視覺順序，而且**重構版面不會弄壞它** |
| **合併焦點** | `MergeSemantics` | 「圖示 + 文字」合成一個焦點，否則同一顆按鈕會被唸兩次 |

### 9.2 ★ 最漂亮的一個例子：停用 + 「已停用」讓體驗更精確

忙線中停用主按鈕，是唯一能真正防重複請求的做法（第 1.1 節）。
再加上 TalkBack 會把 `enabled: false` 唸成「已停用」，兩件事合起來更好：

| 情況 | 使用者體驗 | 完整嗎 |
|---|---|---|
| **只有 App**（TalkBack 關） | 按鈕變灰、標籤改成「正在登入…」、**我們的 TTS 播報「正在登入，請稍候」**、震動一下 | ✅ **完整可用** |
| TalkBack 開著，但我們沒標 `enabled` | TalkBack 只唸得出按鈕標籤，**唸不出「已停用」**，使用者會以為按鈕正常卻按不動 | ⚠️ 仍可用，但少了一層資訊 |
| **兩者都有** | 使用者聽到「正在登入，已停用」 | ⭐ 最好 |

**修正我原本的說法**：我先前寫「少了任何一半都會壞掉」，那是錯的。
App 自己的播報已經把「正在跑」講清楚了，**功能上不缺任何東西**。
TalkBack 的 `enabled` 狀態是**額外的精確度**（明確說是「已停用」而不是只說「正在登入」），
不是可用性的前提。

形狀是這樣：**我們的狀態機負責正確性，TalkBack 負責把正確性講得更精確。**
而不是「一個負責功能、一個負責說明」。

### 9.3 ★ 第二個例子：把按鈕藏進 TalkBack 的選單，同時滿足「簡潔」與「不誤觸」

「解除綁定」這種動作有兩個需求在拉扯：

- **簡潔**要求畫面上少一顆按鈕
- **不誤觸**要求它不要跟別的按鈕相鄰

用 `CustomSemanticsAction` 可以把它放進 TalkBack 的**本機內容選單**：
使用者滑到「Google 已連結」這一項，上滑再右滑，選單裡就會出現「解除綁定」。
畫面上因此**不需要那顆按鈕**，而功能仍然完全可達。

⚠️ **但不能只做選單。** 低視力使用者若沒開 TalkBack 就完全碰不到它。
所以規則寫成：**功能必須有畫面上的入口；本機內容選單是給螢幕閱讀器使用者的加速通道。**
只在一個地方做，就是無障礙退步。

### 9.4 不能跟 TalkBack 搶的東西（四條禁令）

| 禁令 | 為什麼 |
|---|---|
| **不用 `GestureDetector(onTap:)` 承接非語意元件** | TalkBack 完全看不到它。要嘛用真正的按鈕，要嘛給 `Semantics(onTap:)` |
| **不讓 `Semantics(label:)` 與子層 `Text` 重複** | 同一句話會被唸兩次。用 `MergeSemantics` 或 `excludeSemantics` 二選一 |
| **TalkBack 開著時不發自己的 TTS** | 兩隻聲音疊在一起，比沒有聲音更糟（見第 3 節的分流表） |
| **不用單指拖曳做自訂手勢** | 單指拖曳是 TalkBack 的「探索」手勢，搶過來就等於把探索功能弄壞 |

### 9.5 播報長度上限：**唸完約 3 秒**

TalkBack 唸完一句需要時間。如果狀態播報太長，使用者還沒聽完就滑到下一項，
**那句話會被截斷**，而他不會知道有東西沒聽到。

所以規則訂成「**唸完約 3 秒**」，換算成長度是：

| 語言 | 上限 | 依據 |
|---|---|---|
| 中文 | **≤ 12 字** | 中文 TTS 約 4 到 5 字／秒 |
| English | **≤ 40 字元** | 英文 TTS 約 12 到 15 字元／秒 |

這條規則由測試強制（`app/test/auth_strings_test.dart`），不是靠人記得。

> 中途修正：我原本只寫「≤ 12 個字」，那是只適用中文的規則。
> 英文用同一個數字會把句子壓到無法辨識（`Signing in` 剛好 10 個字元，
> 但 `No fingerprint set up` 有 22 個）。所以改成用「**時間**」當標準，
> 長度限制是它的換算結果。

**即時播報與畫面文字是兩份不同的文字。** 錯誤的詳細說明放在畫面上讓
使用者自己滑過去讀，即時播報只給最短的那一句：

| | 即時播報 | 畫面文字 |
|---|---|---|
| 連不上網路（中文） | 「連不上網路」（5 字） | 「連不上網路。引導功能不受影響，可以先選『稍後再說』。」 |
| 連不上網路（英文） | `No network`（10 字元） | `Cannot reach the network. Guidance still works, or choose Not now.` |

### 9.6 焦點管理的規則

| 時機 | 做法 | 理由 |
|---|---|---|
| 進入頁面 | 把焦點設在**標題**（`Semantics(header: true)`），**不另外發自己的 TTS** | TalkBack 會朗讀取得焦點的元素；我們再唸一次就是雙重 |
| 狀態變化 | `liveRegion` 播報，**焦點不動** | 焦點亂跳比聽不到更讓人迷失 |
| 錯誤出現 | `liveRegion` 播報 + 錯誤與「重試」排在**焦點順序的相鄰位置** | 使用者下一滑就到得了出口，不必自己找 |
| 登入成功 | 換頁並讓新頁面標題取得焦點 | 使用者要知道「畫面換了」 |
| 對話框 | 交給 Flutter 的路由語意；**對話框標題要用 `Semantics(header: true)`** | 焦點被圈在對話框內，出口不會跑到背景頁 |

⚠️ **對話框的標題是否會被 TalkBack 自動唸出來，我沒有實測過。**
保險做法是明確給標題 `Semantics(header: true)`，並在真機上確認。

### 9.7 其他要配合的 TalkBack 能力

| 能力 | 我們要做的 | 不做的後果 |
|---|---|---|
| **點字顯示器** | 標籤必須是**完整的詞**，不能是圖示或縮寫 | 點字上只出現一個沒有意義的字元 |
| **開關控制 / 鍵盤** | `OrdinalSortKey` 同樣服務這一群人 | 焦點順序變成 widget 樹的偶然順序 |
| **朗讀速率調快** | 播報短（9.5）在快速率下更舒服 | 長句在快速率下變成噪音 |
| **螢幕閱讀器關著** | 我們自己的回饋（TTS + 觸覺）接手 | 完全沒有回饋 |
| **密碼遮蔽** | 用 `obscureText: true` 交給平台 | 自己實作遮蔽會讓 TalkBack 唸出內容 |
