## 0. 這份文件回答什麼

使用者問了兩件事：**現在能不能接 GPS 導航 API，以及能不能接識字（OCR）API。**

結論先講：

| | 可行性 | 價值 | 建議 |
|---|---|---|---|
| GPS 導航 | 高（但不該接地圖 SDK） | **中**（上限是粗略路線進度） | 接，但**降級為輔助** |
| 識字 OCR | 高 | **高** | 接，但**必須按需啟動** |
| **視覺地標定位** | 高（**零新依賴**） | **最高** | **這才是主線** |

---

## 1. 先換掉問題

「用哪個定位 API」是錯的問題。對一條**固定的示範路線**（調景嶺站 → 彩明苑天橋 → 彩明商場），
需要的是路標級判斷，不是連續座標：

> 「我在**天橋入口**」而不是「22.3051, 114.2532」

問對之後答案就變了，因為**我們已經有一台每秒看五次的相機**。

---

## 2. 決定一切的那道閘：`objective_c`

`app/pubspec.yaml` 記著：本倉庫**路徑含空格**，任何拉進 `objective_c` 的依賴都會讓建構失敗，
且它在**所有平台**都跑。`permission_handler`、`path_provider`、`camera` 都因此被砍掉。

**任何新功能的第一個問題都是：它會不會引入 Flutter plugin？**

### ★ 本專案的繞道

我們**已經有自己的原生插件**（`VisionPlugin.kt`），而且**只做 Android**。所以位置與 OCR 可以：

```
build.gradle.kts 加一行 Gradle 依賴（不是 pub 依賴）
        ↓
在 VisionPlugin 暴露一個 method channel 方法
        ↓
Dart 端呼叫，零新 Flutter plugin
```

**完全避開 build hook 風險。** 代價是自寫 Kotlin，且只有 Android
（但 iOS 本來就需要一台 Mac，不算新增限制）。

> 注意：現成 Flutter 套件（`geolocator`、`google_mlkit_text_recognition`）**是否安全未經查證**。
> 先前查 `shared_preferences` 時吃過一次假陽性的虧。而且**直接依賴乾淨不等於可建構**，
> `objective_c` 是從 build hook 進來的，只有真跑一次 Gradle 才算數。
> **既然繞道成本很小，不建議去賭現成套件。**

## 4. 建議架構：三層混合

**不做通用定位。** 三層，只有第三層需要新東西：

| 層 | 用什麼 | 角色 | 現況 |
|---|---|---|---|
| 1 | **視覺地標狀態機** | 主定位，逐路標 | 已有推論結果，**缺標註** |
| 2 | **PDR**（計步 + 陀螺儀方向） | 補地標之間的空白 | 零權限，約 100 行 |
| 3 | **GPS** | 起點粗篩 + 走偏偵測 | 要權限，**可選** |

**GPS 不是被取代，是被降級**，降到它真正擅長的角色。

---

## 5. 為什麼視覺地標是第一選擇

50 類裡本來就有路標：`footbridge_entrance`、`footbridge_railing`、`escalator`、
`shop_front`、`tactile_paving`、`zebra_crossing`。

所以定位可以做成**在偵測結果上的狀態機**：

```
看到 footbridge_entrance            → 進到「天橋入口」
看到 footbridge_railing 持續        → 進到「在天橋上」
看到 shop_front 且 railing 消失     → 進到「接近商場」
```

優點是壓倒性的：

- **零新 API、零新權限、零新依賴**（連 Gradle 都不用動）
- **在天橋底下、商場裡照樣工作**，而那正是 GPS 最差的環境
- 複用已在跑的推論管線，**不多花 CPU**
- 它其實就是 `PROJECT-STATUS` 上已列著的「**導航決策引擎**」：
  **那不是另一個模組，就是這個**

### 業界佐證

兩個真實的視障導航產品：**NaviLens**（高密度光學碼，遠距可讀）與 **GoodMaps**（視覺定位）。
兩者都**不以 GPS 為主**，都是視覺 + 慣性 + 信標的混合。
這不是偏好，是這個領域的共識做法。

---

## 6. 視覺地標的代價（必須誠實）

它不是免費的，成本從「接 API」搬到「資料與設計」：

1. **地標要夠有辨識度**。若天橋上連續 30 公尺都是同樣的欄杆，狀態機會卡住，
   需要選出沿途**可區分**的特徵點。
2. **需要那條路線的標註資料**，也就是目前**拿不出手機**的那批擷取。
   **又是同一個瓶頸。**
3. **只對走過的路線有效**。但示範路線本來就是固定的，所以不算缺點。

---

## 7. GPS 的真正角色

- GPS 能回答：「你在調景嶺站附近」
- GPS **不能**回答：「走天橋左邊那條」「前面第三間鋪轉彎」

香港高樓密集區與天橋底下精度更差，而示範路線正好是這種環境。

**離線衝突**：整個產品的前提是離線可用，雲端導航 API 會打破它。
若只需一條預先算好的路線，把它當**靜態折線存進 APK** 就沒這個問題。

**不需要地圖 SDK。** 全盲使用者沒有地圖可以看。Android 自己的 `LocationManager`
就能給座標：**不要 API key、不要計費、不要授權地圖資料。**

## 8. 識字（OCR）

用途明確：讀招牌、門牌、指示牌。對盲人在香港街頭很實用。

**技術首選**：Google ML Kit 裝置端文字辨識（支援繁體中文），免費、離線、快。

### ⚠️ 硬體限制：CPU 競爭

本機（SD685，**沒有 NNAPI/GPU delegate 可用**）現在跑一個 int8 模型就已經是
**5.2 fps、每次推論約 187 ms**，CPU 基本上滿載。**再加一個 OCR 同時跑會互搶 CPU。**

### 所以設計必須是「按需啟動」

這也更合理：

- 「讀招牌」本來就是**刻意的動作**：對準、停住、讀
- 持續跑 OCR 會把障礙物播報洗掉（`Announcer` 有冷卻，經不起灌訊息）
- 使用者不需要知道「牆上有 47 個字」

**這代表要新增一個互動模式**（識字模式），而它的觸發方式
**必須不與 TalkBack 的手勢衝突**。這是設計問題，不只是 API 問題。

---

## 9. 權限

GPS 需要 `ACCESS_FINE_LOCATION`，是新的**執行期權限**（目前只問相機）。

按 `docs/A11Y-ENTRY-AND-AUTH.md` 第 3 節的規範：權限必須**先說再問**，
而且要**教互動不教位置**。定位權限在 Android 上還伴隨「你為什麼要我的位置」的信任問題，
Play 商店也要宣告資料安全。**不能默默加。**

### 13.1 已驗證的事實（不是推論）

1. **離線成立，直接從 APK 查證。** APK 內含
   `lib/arm64-v8a/libmlkit_google_ocr_pipeline.so`（10.5 MB）與
   `assets/mlkit-google-ocr-models/gocr/.../Hani_ctc/...`（Hani = 漢字）。
   **模型確實在 APK 裡**，所以不需連網、不依賴 Play Services 下載。

2. **體積：+8.6 MB**（debug APK 210.5 → 219.1 MB，壓縮後）。
   未壓縮約 +28 MB，因為三個 ABI 各帶一份 native library。

3. **建置時間：897 秒**（全新檢出、無快取的首次建置）。

### 13.2 ★ 兩個反直覺的坑（都已寫進程式註解）

**(a) 「綁定版 vs 未綁定版」的機制跟直覺不同，先前的註解是錯的。**

`com.google.mlkit:text-recognition-chinese` 這個 AAR **本身幾乎是空的**
（classes.jar 只有 2 個類別）。公開 API 其實住在 **play-services-** 那兩個
傳遞依賴裡：

```
com.google.mlkit.vision.text.TextRecognition
    -> play-services-mlkit-text-recognition-common-19.1.0
...vision.text.chinese.ChineseTextRecognizerOptions
    -> play-services-mlkit-text-recognition-chinese-16.0.1
```

所以 `play-services-` **不是「不能用的另一條路」，它是這條路的一部分**。
「離線」的真正來源是 `text-recognition-bundled-common`（17.5 MB）。
先前的註解寫「不能用 play-services- 那條，會走按需下載」——**那是錯的**，已更正。

**(b) `check_kotlin_compiles.py` 有兩個假陽性來源，都已修掉。**

- **快取路徑寫死。** 原本只找倉庫內的 `.tools/gradle`，但沒載入 `.env.ps1`
  時 Gradle 用的是 `~/.gradle`。於是門檻會看到**過期的快取**，把已解析成功的
  依賴報成 `unresolved reference`。現在會搜尋兩者（`$GRADLE_USER_HOME` 優先）。
- **依賴清單不完整。** 少了 `play-services-mlkit-text-recognition-common` 就會
  報 `unresolved reference 'TextRecognition'`，而錯誤訊息長得跟真的編譯錯誤
  一模一樣。**這一項在本次實作中真的踩到了，浪費了好幾輪。**

兩者合起來的教訓：**這個門檻的假陽性最貴**，因為它會讓人去改沒壞的程式碼。

### 13.3 誠實的邊界

- **辨識品質完全未驗證。** 官方只說支援 Chinese **指令碼**，不分繁簡。
  香港招牌是繁體 + 中英混排 + 特殊字體，**只能用你們自己的照片測**。
  這是整個 spike 唯一決定成敗的一項，而它還沒被測。
- **效能完全未量。** 所有耗時欄位（`decodeMs` / `ocrMs` / `totalMs`）都是為了
  真機量測而加的，目前**一個真實數字都沒有**。
- **沒有 UI、沒有播報。** `readText()` 只是能力；接成「識字模式」
  （含不衝突 TalkBack 的觸發手勢）是第 7 項，尚未開始。
- **iOS 未實作。** `VisionPlugin.swift` 沒有對應方法，Dart 側會退化成
  「讀不到」而不是崩潰（已用 `MissingPluginException` 處理）。

### 13.4 為什麼走 JPEG 繞一圈（設計取捨，供之後檢討）

`readText()` 用既有的 YUV→JPEG→Bitmap 路徑取得 Bitmap，而不是純 CPU 直接
YUV→ARGB。理由是後者的色彩轉換數學**容易寫錯且不報錯**，錯了只會讓 OCR
準確率默默變差。代價是多一次編解碼，所以把 `decodeMs` 單獨回報——
**若這一段佔了大頭，那是我們自己的問題（該改直轉），不是 ML Kit 慢。**
